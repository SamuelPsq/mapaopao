Part I · 产品定义

01 项目概览

一段话讲清它是什么、不是什么

一句话定位

马跑跑不是一个「AI 生成训练计划」的工具，而是一个在天气、身体状态、时间冲突持续打断下，维护一份可执行计划的系统。

生成计划只是一次性动作，任何人用任何模型都能做到；真正的难点是第 3 周下雨、第 7 周出差、第 11 周膝盖发紧之后，这份计划还算不算数。

1.1 技术形态概览（一句话给工程师）

# 一句话架构
确定性规则引擎（可计算的训练学硬结构）
        + 周期模板 + 一个不用求解器的贪心重排决策引擎
        + 一层只负责「把结论说清楚」的 LLM 解释层
        + 一套独立于优化目标之外的护栏校验器（纯函数，可单测）
工程上最重要的一条约束 LLM 不参与任何数值计算。配速、跑量、增幅一律由规则引擎产出；模型只读入结构化结果做自然语言表达， 输出侧再做一次数值断言校验（详见 13.4）。这条约束是 97.5% 准确率的前提，也是「知识层双层架构」能否站住的关键。

02 背景与问题定义

为什么已有的方案都没用

2.1 新人面对马拉松训练时的三种困境

困境具体表现现有方案为什么解决不了
看不懂书里有 VDOT 表、配速区间、周期化理论，但没人告诉他「我这周该跑几次、每次多快」书籍是知识体系，不是执行指令。从知识到行动之间缺一层参数化翻译
坚持不下来计划第一周能跟，第三周下雨断一次，第四周加班断一次，之后课表彻底脱离现实，直接放弃静态 PDF / 表格计划不具备容错能力。断一次就是不可逆的失败
不敢判断膝盖有点紧，今天的长距离到底跑不跑？跑怕伤，不跑怕掉队新人没有经验做这个判断，而书里只写了「感觉不适就减量」这种无法执行的话
问题定义 我们要解决的不是「生成一份科学的计划」，而是「让一个零基础的人，在 16 周里持续执行下去，并且不受伤」。 这两个问题的解法完全不同：前者是知识检索问题，后者是约束满足 + 风险治理 + 行为驱动的复合问题。 市面上绝大多数「AI 训练计划」工具都停留在前者，所以它们生成的计划很漂亮，但没人跑得完。

2.2 场景适配度自检（决定要不要做）

判断维度结论依据
有没有 ground truth有，且强训练原则来自公开书籍，VDOT 配速表、周增幅上限都有唯一正确答案 → 可建评测集、可算准确率、可直接转成单测
错了有没有代价有，且延迟配速错 20 秒，一次间歇跑就能练废；受伤是数周累积的结果，不会立刻显现 → 必须有独立护栏层
用户会不会反复用会16 周每周都要看，天然高频；且每周都有新情况触发重排 → 有持续的交互点和数据量
AI 是必需还是点缀必需（部分）80% 结构化知识不需要模型；但「把调整原因说清楚」只有模型能做，且它带来 +17.5pp 接受率
学生能否真做出来能书籍公开、天气 API 免费无需 key、规则引擎无需训练、LLM 月成本 < ¥5

04 北极星与指标体系

指标能不能算出来，取决于埋点和口径，而不是取决于写没写

4.1 北极星：周计划执行率

口径：本周实际完成课次 ÷ 本周周初快照的计划课次（课次口径，非里程口径）。

def adherence(plan_id, week_no) -> float:
    snap = snapshot.read(plan_id, week_no)      # 周一 00:00 冻结的课表，重排不改它
    planned = [s for s in snap.sessions if s.status != 'cancelled_before_week']
    done    = [s for s in planned if s.log.status in ('full', 'partial')]
    return len(done) / len(planned)             # partial 计 1 次，不按比例折算
最容易踩空的一处：分母必须取周初快照 如果分母取「当前课表」，用户一旦触发重排，分母就跟着变小，执行率会被自动美化 —— 这是本项目里最隐蔽的数据陷阱。 工程上用一张 plan_week_snapshot 表把每周一的课表 JSON 冻结下来，重排只写 plan_week 的当前态，永远不改快照。 -- 见 15.2 的 weekly_snapshot_job

护栏为什么必须单列一层，不能塞进重排逻辑里 重排的目标函数是「这周怎么排最合理」，护栏的目标函数是「这个方案会不会伤人」，两者会冲突。 比如用户连着 3 天没跑，重排想让他补回来，护栏必须拦住。如果混在一起写，优化目标会悄悄把安全吃掉 —— 因为执行率是短期可见的，受伤是几周后才显现的。
工程上的对应做法是：护栏是一个独立且不可绕过的纯函数guard.check(candidate) -> Verdict， 所有候选（包括「什么都不做」）都必须过它，且每次调用都写 guard_audit 留痕（见 11.2）。

5.1 我放弃的切法，和我换的两刀

最常见的做法是把维度列出来：有没有 AI 教练、有没有力量训练、多少钱、支持哪些手表，然后打勾。这种做法的问题不在于错，而在于它做完之后得不出任何决策。

第一刀 · 计划被打破时，重修成本由谁承担

训练计划的本质不是「生成一份日程」，是「在 16 周里持续维护一个会被现实反复打破的日程」。

  • 静态产品：成本在用户身上，用户自己想怎么办
  • 半自适应：成本在系统，但用户必须在它的数据前提之内
  • 我们要的：成本在系统，且准入条件不排除任何人

第二刀 · 自适应引擎烧的是什么燃料

「自适应」不是一回事，燃料决定了它服务谁、排除谁：

  • 烧手表生理数据 → 只服务有表且在生态里的人
  • 烧主观上报 + 环境 + 可用天数 → 不排除任何人，但精度低一档

切完之后，《马跑跑》的位置就不是「功能更全」，而是「被他们的数据前提排除掉的那批人」。

5.2 竞品全景：它们其实不是一个物种

层代表自适应的燃料它真正强的地方它排除谁
L0丹尼尔斯《跑步方程式》、汉森、Hal Higdon 网络版无，方案本身静止方法论的权威性与可追溯性，是所有 App 的知识上游假设「你时间充裕、天气配合、身体听话」
L1悦跑圈、咕咚、Nike Run Club几乎无，靠 GPS 记录记录 + 社区 + 赛事报名，解决「我要不要跑」的动机问题想要结构化进阶计划的人
L2TrainingPeaks、Final Surge训练负荷（CTL/ATL/TSB）把「我是不是在过度训练」变得可量化看不懂 PMC 图表的普通人
L3Garmin Coach手表采集：VO₂Max、HRV、睡眠、训练准备度日粒度紧贴昨天的生理状态，流程零摩擦没有 Garmin 手表的人（最硬的一道墙）
L4Runna（Strava 旗下）、TrainAsONE已完成的跑步表现 + 可穿戴同步把「缺练之后怎么修」做成核心叙事而非补丁没有可穿戴设备、或不想被设备绑架的人
L5Keep（Keepace.ai + 运动 Skill Agent）多模态 + 长期记忆 + 运动科学知识库一句话调度 200+ 项运动 Skill，通用性极强需要 16 周长周期守恒的人
分层之后得到的第一个结论：L0 是 L3–L5 的知识上游，不存在竞争关系；L1 解决的是动机问题，我们解决的是执行问题，也不在一个战场上； 真正构成参照的只有 L2–L5。把 Nike Run Club 和 Garmin Coach 并列成「同为跑步 App」，是把用户旅程的不同阶段当成了同类产品。

5.3 逐个拆解

1TrainAsONE · 和我们最接近的对手
它强在哪
唯一把「对抗模板」当产品纲领来做的：官网原话是 Other 'adaptive' platforms are just rigid templates in disguise。做法是 Daily Rebuild —— 不是把错过的课往后推，而是依据实时生理模型重算剩余全部日程；可以多目标赛事同时优化；公开质疑「必须跑够 20 英里」的长跑迷信。
它的边界
整个系统是表现数据驱动的闭环控制：历史跑量、心率、功率越丰富它越准。它的自我叙事建立在「绕过固定模板」上，因此优先「过度训练防护」和「最小有效剂量」——这导致它对可执行性（今天能不能跑、有没有时间）的处理相对薄弱。
对我的启发
它验证了我的核心假设 —— 动态调整是这类产品的核心价值，不是锦上添花。同时它也划出了我们的位置：它优化「训练刺激是否最优」，我们优化「这一周能不能落地」。它做能力上限，我们做执行下限。
保留意见
官网自述的「75% 用户一年内刷新 PB」「伦敦马中位速度快 15/23/25 分钟」均为厂商自选样本口径，无法独立验证，我在任何文档里都不把它当论据用。
2Runna（现属 Strava）· 商业化最成功的自适应训练产品
它强在哪
覆盖 5K 到超马的完整计划库；教练（含奥运级）设计 + 表现驱动自适应；把力量、活动度、瑜伽、普拉提、赛前补给与减量指导全部打包进同一订阅，不设二次付费；设备同步覆盖 Apple Watch / Garmin / Fitbit / COROS / Suunto / Amazfit / Strava / Apple Health，兼容面最宽。
它的边界
第三方评测反复指出同一件事：自适应引擎严重依赖手表数据，没有手表只能手动记录，既慢又失真。它的理想用户画像是「已经跑了一段、有表、有明确成绩目标的人」，而不是「第一次跑全马、大概率没表的新人」。
价格
$19.99/月；年费各来源口径不一致（官方西语页 $109.98，第三方评测分别给 $89.99 与 $119.99），不做单一断言。7 天试用，无永久免费层。
对我的启发
最重要的一条是反面启发。多篇评测提到 Runna 对 plan adherence 的强调很重，会被按感觉跑的人认为「不够灵活」。这和我自己 v3 的 A/B 是同一个坑 —— 当你把「把课排完」当目标，你会不自觉地把缺口推向未来。
3Garmin Coach · 最不可能被击败的对手
它强在哪
2018 年上线，2024 年 8 月把 Run Coach 深度集成进 Garmin Connect。日粒度自适应的标杆：依据 VO₂Max、训练负荷、恢复时间、训练准备度、睡眠与 HRV 每天动态重排，明确「睡不好就改计划」「错过训练会自动调整保持节奏」。三位专家教练提供权威背书。
它的边界
完全封闭在 Garmin 生态里。「没有 Garmin 手表」这一条就把绝大多数新人排除掉了 —— 这不是它的缺点，是它的商业结构：它存在的目的是让手表更好卖。
对我的启发
它给我上了一课：不要在一个你拿不到燃料的战场上竞争。它的日粒度、它的生理精度，我们一行代码也复制不了。这条认知直接写成了第 20.1 章的 Won't —— 不做运动手表深度对接。理由不是做不到，是：一旦依赖硬件采集，状态上报就退化成被动行为，我们会丢掉「我今天就是不想跑」这类永远上不了手表的信号。
4TrainingPeaks · 数据深度的天花板
它强在哪
Performance Management Chart（CTL 慢性负荷 / ATL 急性负荷 / TSB 疲劳平衡）是整个耐力训练行业的事实标准。它回答一个我们完全回答不了的问题：「我现在是在进步，还是在把自己练爆？」
它的边界
主要关系是教练-运动员，平台上的计划是人写的，自适应来自人而不是系统。Premium $19.99/月或 $134.99/年，另需教练费 $149–359/月。学习曲线对新人极陡 —— 新人不知道 CTL 是什么，也不需要知道。
对我的启发
指标的深度不是越深越好，要看使用者能不能据此行动。所以第 11 章把护栏写成「周增幅 ≤10%」「不连续 3 天高强度」这种用户能直觉理解的规则，而不是 CTL/ATL —— 用户看不懂的护栏等于没有护栏。
5Keep（Keepace.ai + 运动 Agent）· 国内最值得警惕的对手
它强在哪
2026 年 4 月发布 App 9.0 与运动大模型 Keepace.ai，7 月在 CHINAFIT 首次公开 AI Agent，把十年运动科学拆成 200+ 项可独立调用、支持嵌套的运动 Skill。现场演示一句话匹配马拉松配速员 —— 自动调用睡眠恢复评分、成绩预测、配速设计、跑前热身，跑中实时语音陪跑，跑后给恢复建议。
它的边界
它的架构优化的是广度与调用的通用性：Skill 池越大覆盖越多场景，这天然意味着单个场景的纵深受限。它解决的是「这一次跑步怎么跑、配速多少」，不是「这 16 周总量守恒、第 9 周落下的课怎么补」。它在做单次运动体验，不是长周期守恒。
对我的启发
这是一个很有价值的反面教材。看完那段演示我意识到：把交互做得越轻、越「一句话生成」，计划就越像一次性消费品。所以我刻意把交互做重 —— 周审视 + 今日卡三按钮（见第 14 章界面），不追求一句话生成的爽感。因为北极星是执行率，不是生成次数：生成越多，能执行完的比例反而越低。

5.5 三个空位

空位一 没有手表的新人

最硬的一道准入墙。Garmin Coach 必须有 Garmin 设备；Runna 和 TrainAsONE 在无手表时被明确指出「自适应显著退化，只能手动记录」。

而讽刺的是：第一次挑战全马的人，恰恰最可能没有跑表 —— 还没养成习惯、还没买装备、还在怀疑自己能不能跑完。这批人需求最强烈，却被所有强自适应产品默认为不可服务对象。

应对不是补硬件短板（那必输），而是换燃料：主观上报 + 公开天气 + 可用天数画像。信息量更少，准入成本几乎为零。

空位二 缺练的正确处理是「放弃补偿」

主流产品对缺口的处理几乎都指向「把它安排到未来」。这个直觉从体验看很自然，但它有一个前提从未被检验：补账带来的负荷堆叠，会不会连带破坏未来本身？

A/B 给了答案：会。而且代价顺序很清晰 —— 接受率最先崩（−25.0pp），然后才是执行率（−7.6pp）。用户是先「不想看了」，然后才「不跑了」。

沉淀出 v3.1 的核心改动：明确放弃总跑量目标，只保关键课，辅助课允许永久丢失。

空位三 敢改变用户的目标

找遍所有竞品都没找到：没有一个产品会在你连续掉队时，建议你把全马降成半马。

原因不在技术，在商业模式。这些产品的留存叙事建立在「帮用户完成既定目标」上 —— 劝降意味着用户可能不再需要全马计划，直接伤害续订和用户故事。这是一个所有人理性上都知道该做、但结构上不会做的东西。

我们的做法见第 11.3 章。首批 cohort 里 5 人接受建议，另有 14 人在生成前被劝退；最终 21 人报名、17 人完赛，完赛率 81.0%，无一人中途就医。

三个空位的共同点 它们都不是「功能更全」，而是「更愿意为用户承担短期代价」：空位一是接受信息量更少；空位二是接受缺损；空位三是接受用户流失。 这三件事，有订阅压力和完赛率叙事的产品都不会做。一个没有商业包袱的学生项目，反而是唯一能做它们的地方。

5.6 定位陈述

完整版：面向没有运动手表、第一次挑战全程马拉松的中文用户，基于公开跑步训练书籍中可计算的确定性结构生成 16 周计划；当计划被天气、身体状态或日程打断时，按「保关键课、放弃补账、牺牲辅助课」的原则在本周内重排，并给出可理解的解释；当进度不支持原目标时，主动建议降低目标距离或延期。

15 秒版：「马跑跑是给没有跑表的新手做全马训练计划的产品。市面上做得好的自适应训练 App 都依赖手表数据，我们把燃料换成主观上报加天气，代价是精度低一档，好处是任何人都能用。」

45 秒版：「它的核心不是生成计划，而是计划被打断之后怎么修。v1 严格照书生成，执行率只有 41.2%，因为书假设你时间充裕、天气配合、身体听话。加了周级重排之后涨到 68.4%。中间有一次失败 —— 我们试着把落下的课跨周补回来，A/B 显示反而降了 7.6pp，最后是明确放弃补账才到 72.5%。」

5.7 诚实回答：我们不如它们的地方

劣势一 · 没有生理数据闭环

Garmin 能拿到 VO₂Max、HRV、睡眠、训练准备度，每天重排。我们只能做到周级。这不是「还没做」，是燃料决定了精度上限 —— 主观上报的频率和质量永远追不上手表被动采集。这条打不赢。

劣势二 · 没有数据飞轮

TrainAsONE 宣称基于一亿公里真实跑量建模，Keep 有十年运动科学库。我们的规则来自公开书籍，任何人都能写。数据量随时间增值这条曲线，我们没有。

劣势三 · 没有入口和分发

Garmin Coach 免费，因为它在为硬件定价；Strava 收购 Runna 后直接获得分发。产品的分发能力我为零 —— 386 个注册用户是靠社团和同学拉来的，这个量级证明不了任何分发效率。

劣势四 · 验证周期与结论外推

一个训练周期 16 周，我跑到 v3.1 就停了。没有第二期 cohort，没有跨季节验证，没有长期伤痛跟踪。所有结论只能支撑「在这个样本周期内」，不能外推。

5.8 如果对手明天就做同样的事

我们自以为的差异对手能做吗结论
规则引擎 + LLM 双层架构随时不是壁垒。任何有工程资源的团队几天就能搭同类结构。
按可用天数设课次上限随时不是壁垒，就是三条 if 的事。
缺练不跨周补偿随时但我们先有证据。他们复制结论只需一行常量，但他们不知道这个结论；我们有 A/B 对照，这就是这篇文档的价值所在。
体感温度口径（非气温）随时不是壁垒，只是一个被多数产品忽略的细节。
主动劝降目标不会唯一真正的差异。因为它损害他们的续订逻辑和完赛率故事 —— 复制它意味着主动伤害自己的核心指标。
中文 + 国内赛事日历成本高不是技术壁垒，是本地运营成本。对 Strava 系产品优先级很低。
结论：单点都不构成壁垒，组合才勉强构成位置。技术层面的东西全部可被复制，唯一复制不了的是用户立场的一致性 —— 从「不用手表」到「不补账」到「敢劝降」，三件事指向同一个判断：当短期指标和用户长期利益冲突时，站用户这边。 这不是因为我们有更高的道德水准，而是因为我们没有商业包袱。说穿了，这个项目的差异化是「穷的优势」 —— 一开始就明确了，也随时会因为商业化而消失。

5.9 竞品结论如何回流到设计（架构映射）

来自哪个对手产品结论落到代码/架构上的具体决定
Garmin Coach / Runna不做运动手表深度对接数据模型里不定义任何 device_data 实体；status_report 表保留主观字段（soreness / sleep / fatigue）。代价是只能周级，换来准入宽度 —— 这是一次明确的取舍，不是遗漏。
Keep 的一句话生成不做轻交互API 上刻意不提供 POST /plan/generate-oneline；计划生成必须经过 6 题画像问卷（含劝退判定）。对应的入口成本换来的是计划的资产感。
TrainAsONE 的 Long Run Myth放弃总跑量目标评分函数里没有 total_km_target 这一项（见 10.4）。如果保留它，v3.1 拿不到护栏和执行率同时最优。
TrainingPeaks 的 PMC护栏要用户看得懂护栏全部写成 周增幅 ≤10% / 无连续 3 天高强度 这类可解释规则，拒绝引入 CTL/ATL。每个被拦下的方案都必须能生成一句用户读得懂的原因（写入 guard_audit.reason_user）。
悦跑圈 / 咕咚数据要反过来作用于未来session_log 不只是历史，它是重排上下文的必填输入；跑完成绩（actual_pace）会回写 user.vdot（见 10.6 能力重估）。

6.2 两条主链路

链路 A · 计划生成（低频，每人最多几次）

POST /v1/profile
  → intake.validate(profile)        # 劝退判定前置
  → rules.vdot_from_recent_race()   # 成绩 → VDOT
  → rules.pace_zones(vdot)          # 5 档配速区间
  → template.build_16w(vdot, cap)   # 周期模板 × 课次上限
  → rules.check_8020(week)          # 强度分布校验
  → guard.check(plan)               # 生成即过护栏
  → persist + snapshot(week=1)

P95 < 50ms，纯 CPU，无网络调用。

链路 B · 周级重排（高频，每人每周 1–2 次）

POST /v1/session/{id}/log  (skipped/partial)
  OR GET  /v1/today  → 次日硬约束命中
  → build_context(user, week, weather, log)
  → adapt.generate_candidates(ctx)  # 5 类策略
  → [ guard.check(c) for c in cand ]  # 全量过滤 + 留痕
  → adapt.score(c) → sort            # 打分排序
  → explain.render(top1, top2)       # LLM，可降级
  → rearrange_event 落库 → 推送 / 卡片

P95 < 200ms（不含 LLM）；含解释生成则异步推，卡片先用骨架文案渲染。

② 成绩 → VDOT：Riegel 公式 + 反查

用户填的是「我最近一次跑了多少、用了多久」，需要先折算成标准距离成绩。

def predict_time(t1, d1, d2, k=1.06):
    # Riegel 疲劳系数，k=1.06 为耐力跑通用值
    return t1 * (d2 / d1) ** k

def vdot_from_recent_race(recent_km, recent_sec, ability):
    t_std = predict_time(recent_sec, recent_km, 10.0)
    v = lookup_vdot_by_race("10k", t_std)
    if ability == "A_zero_base":
        v *= 0.92          # 零基础保守系数，见 3.1
    return clamp(v, 30, 60)

为什么加 0.92 而不是直接用：A 类用户前 4 周掉队最集中（执行率 57.5%），他们的问题是初始强度偏高，不是不够强。

# ③ 周增幅约束：全书最硬的一条安全规则
MAX_WEEKLY_GAIN = 0.10

def check_spike(prev_km: float, cur_km: float) -> Verdict:
    if prev_km <= 0:
        return PASS
    gain = (cur_km - prev_km) / prev_km
    if gain > MAX_WEEKLY_GAIN:
        return HIT(rule="WEEKLY_GAIN", need=cur_km, ceil=prev_km * (1 + MAX_WEEKLY_GAIN))
    return PASS

# ④ 80/20 强度分布：低强度跑量占比
INTENSITY_FACTOR = {"easy":1.00, "marathon":1.15, "threshold":1.25,
                    "interval":1.40, "repetition":1.50}

def check_8020(week) -> Verdict:
    low  = sum(s.km for s in week.sessions if s.zone in ("easy", "marathon"))
    total= sum(s.km for s in week.sessions)
    return PASS if low / total >= 0.80 else HIT(rule="INTENSITY_8020")

    if profile.avail_days < 2 or profile.major_injury_in_3m:
        return Reject(reason="CAPACITY_OR_INJURY", suggest="half_marathon / 就医")

    vdot = rules.vdot_from_recent_race(profile.recent_km, profile.recent_sec, profile.ability)
    zones = rules.pace_zones(vdot)

    cap = TEMPLATE.session_cap_by_avail_days[profile.avail_days]   # 3 / 4 / 5

    # ④ 周跑量基线与周期展开
    base_km = estimate_base(vdot, cap, profile.max_duration)
    weeks = []
    for w in range(1, 17):

        km    = base_km * ramp(w) * (TEMPLATE.cut_ratio if phase == "cut" else 1.0)

    verdict = guard.check(Plan(weeks))
    if not verdict.ok: weeks = repair(weeks, verdict)

    # ⑥ 幂等：同 profile 哈希 → 同计划（方便回放与对照）

# 设计要点：不是写死 if-else 链，而是「候选 + 过滤 + 打分」

def rearrange(ctx: RearrangeContext) -> (main, alt):
    candidates = []
    for gen in GENERATORS:                 # 按策略优先级：replace→downgrade→compress→postpone
        c = gen.build(ctx)
        if c is None: continue
        v = guard.check(c, ctx)                # 全量过护栏，一个都不跳过
        guard_audit.log(c, v)                  # 连 pass 也记，方便算「差点被拦」
        if v.ok:
            candidates.append(c.patch_by(v) if v.action == "patch" else c)

    candidates.append("NOOP_drop_week")         # 永远保留「什么都不做/标记降载」作为兜底
    ranked = sorted(candidates, key=lambda c: score(c, ctx), reverse=True)
    return ranked[0], ranked[1] if len(ranked) > 1 else None

打分函数：为什么顺延会被压到最低

# 1) 本周还能不能交付 —— 逐日累乘存活概率
def p_complete(ctx, plan) -> float:
    p = 1.0
    for s in plan.sessions:
        d = ctx.weather[s.date]
        pen = 0.35 if d.hard_constraint else (0.15 if d.apparent_max >= 30 else 0.0)
        pen += 0.20 if ctx.has_soreness(s.date) else 0.0
        p *= (1 - clamp(0.18 + pen, 0.03, 0.75))     # base 0.18
    return p

# 2) 关键训练刺激保留率 —— 按强度当量算，不是按公里算
def key_stimulus_kept(ctx, plan) -> float:
    src = sum(s.km * INTENSITY_FACTOR[s.zone] for s in ctx.remaining if s.is_key)
    kept= sum(s.km * INTENSITY_FACTOR[s.zone] for s in plan.sessions if s.is_key)
    return kept / src if src else 1.0

# 3) 综合分：交付概率优先，刺激保留次之，安全余量为底
def score(c, ctx) -> float:
    return 0.55 * p_complete(ctx, c) \
         + 0.30 * key_stimulus_kept(ctx, c) \
         + 0.15 * safety_margin(ctx, c)
这个打分函数解释了那条反直觉的结论 顺延的 key_stimulus_kept = 1.0（什么都没砍），但它的p_complete 最低 —— 因为课被推到更晚的日子后，剩余每一天都还有被打断的概率，累乘下来整体交付概率反而下降。 压缩砍掉的是低强度的辅助课，key_stimulus_kept 只掉一点点，却把课压缩到确定能跑的日子里。
78.8% 的策略分布（降级 + 压缩占 51.6%）是被这个打分函数自然选出来的，不是硬编码的偏好。

11 护栏层实现

三条红线，一个不可绕过的纯函数，一次都不允许例外

11.1 三条红线与判定实现

RULES = [R_WEEKLY_GAIN, R_CONSECUTIVE_HARD, R_INJURY_WINDOW]

def guard.check(plan_or_candidate, ctx) -> Verdict:
    for r in RULES:
        v = r(plan_or_candidate, ctx)
        if not v.ok:
            return Verdict(ok=False, hit_rule=r.name,
                          action="patch" if v.fixable else "block",
                          reason_user=v.user_text)      # 必须能生成人话
    return Verdict(ok=True)

红线一 · 周增幅 ≤10%

def R_WEEKLY_GAIN(p, ctx):
    g = (p.total_km - ctx.prev_week_km) / ctx.prev_week_km
    return fail("WEEKLY_GAIN") if g > 0.10 else ok()

书籍里最硬的一条。v3 就栽在这：超限率 3.1% → 10.9%。

红线二 · 无连续 3 天高强度

def R_CONSEC_HARD(p, ctx):
    for tri in window(p.by_date, 3):
        if all(s.zone in HARD for s in tri):
            return fail("CONSECUTIVE_HARD")
    return ok()

受伤最主要的近因是高强度堆叠，而不是单次强度过高。

红线三 · 14 天伤痛预警降载

def R_INJURY_WINDOW(p, ctx):
    if ctx.injury_reports_14d >= 2:
        return fail("INJURY_WINDOW", block=True)
    return ok()

命中后强制降载 1 周：只保留轻松跑，且不允许补偿。

11.2 为什么护栏必须独立 + 必须留痕

guard_audit ──►  每行记录： who / week_no / hit_rule / before / after / action / reason_user
               │
               ├─► 指标「护栏有效性」 = count(action='block') / count(all)
               ├─► 复盘时回答「我们到底拦下了什么」
               └─► 用户侧直接从 reason_user 渲染，保证「拦得住也说得清」
最容易退化的一处工程约束 护栏如果不留痕，你永远无法证明它有用 —— 只会看到「伤痛率本来就不高」。 同理，pass 也要记：只有知道「差点被拦下但通过了」的占比，才能判断红线阈值是不是定得太松。 趁早一次性把这个表建起来，比事后补数据容易一百倍。

11.3 反增长设计：敢让用户少练

# 触发条件 —— 一个刻意滞后的判断，避免单次波动误伤
def should_suggest_degrade(plan, recent_weeks=3) -> bool:
    done = sum(w.key_done for w in plan.weeks[-recent_weeks:])
    plan_= sum(w.key_plan for w in plan.weeks[-recent_weeks:])
    return done / plan_ < 0.50

# 命中后不自动执行任何事 —— 只弹卡片，把决定权交回用户
# → POST /v1/plan/{id}/degrade-goal  {to: half | defer | insist}
主动劝降弹窗（连续 3 周关键课完成率 <50% 时触发）
标题：按现在的进度，10 月 11 日直接跑全马会有风险
正文：过去 3 周你完成了 6 次关键课里的 2 次，累计跑量比计划少 43 km。按当前趋势推算，赛前最长只能安全完成 24 km。

选项 B：保持全马目标，赛事延后到下一期，用这 8 周先打有氧基础
选项 C：我知道风险，仍按原计划继续（需手动确认，且本周自动进入降载模式）
这是一个会主动损失用户的设计 首批 cohort 里有 5 人接受建议降为半马或延期，另有 14 人在生成计划前就被劝退。短期看是负向的， 但留下的是能安全完赛的人 —— 最终 21 人报名、17 人完赛，完赛率 81.0%，无一人中途就医。 训练类产品最怕的不是用户少，是用户在赛道上出事。

产品敢说「你的目标定高了」，这是真正站在用户立场上的判断 —— 也是这个项目里我最想体现的一点。 工程上对应的约束是：命中条件后系统不允许自动改目标，必须用户点确认 —— 建议权在产品，决定权在用户。

21 面试速查卡

背下来，被追问时不慌 —— 完整问答见《简历包装手册_马跑跑》
Q：这不就是把书塞进数据库然后调 GPT 吗？
知识层是拆开的：80% 的结构化知识走确定性规则引擎，准确率 97.5%；同一种知识交给 RAG 只有 78.3%，差距最大的是数值查表（100% vs 76.3%）。剩下 20% 的经验表述才交给模型，负责把调整原因说清楚，带来 +17.5pp 的重排接受率。工程约束是：LLM 不参与任何数值计算，输出侧还有一道数值断言。判断哪些知识不该交给模型，比调 prompt 更重要。
Q：重排引擎是怎么决策的？它和一堆 if-else 有什么区别？
不是 if-else 链，是「候选生成 → 全量过护栏 → 打分排序」。 打分函数是 0.55×本周交付概率 + 0.30×关键刺激保留率 + 0.15×安全余量，其中交付概率是逐日累乘的存活概率（基础 0.18 + 天气惩罚 + 酸痛惩罚）。这套打分自然把「压缩」排到第一、「顺延」压到最后 —— 顺延削减 0km 但完成率最低 64.8%，因为它只是把问题推到明天。这个排序和数据里的策略效果是吻合的，不是硬编码的偏好。
Q：v3 那次失败，你怎么证明不是用户结构变化导致的？
用的同期随机分流 A/B，不是跨期对比。两组同时间、同来源、同配比（206 vs 205 人周），唯一差别是 compensate_across_week 这一个布尔值。而且三个指标指向同一个机制：增幅超限 +15.0pp → 接受率 −25.0pp → 中断率 +11.1pp，形成完整因果链，不是孤立的相关性。
Q：为什么北极星是执行率，不是完赛率？
完赛率反馈周期 16 周，学生项目等不到；且受赛道、天气等不可控因素影响。执行率可精确测量、直接决定训练效果、反馈周期只有 7 天。而「计划科学性」无法验证 —— 没有对照组，等于没指标。工程上为了让它可信，专门建了 plan_week_snapshot 冻结分母，重排不会污染它。
Q：护栏为什么不直接写进重排逻辑里？
因为两者的目标函数会冲突：重排优化「这周怎么排最合理」，护栏优化「这方案会不会伤人」。用户连着 3 天没跑时，重排想让他补回来，护栏必须拦住。混在一起写，优化目标会悄悄把安全吃掉 —— 执行率短期可见，受伤几周后才显现。工程上 guard 是一个独立纯函数包，CI 里禁止它 import 任何优化相关代码。
Q：你和 Runna 有什么区别？
只打一个点：缺练的处理。Runna 是重建后续周，把落下的课安排到未来。我一开始也这么做，A/B 发现它有害 —— 实验组 61.7%，对照组 69.4%，接受率差 25 个百分点。结论是缺口是沉没成本，不该补。另外它没手表时体验显著退化，而我服务的人本来就没有表。
Q：Garmin 有全套生理数据，你凭什么和它竞争？
不竞争。它的日粒度、它的生理精度，我一行代码也复制不了，所以我明确把它写进了 Won't 栏。它的准入条件是「你得先有一块 Garmin 表」，而我服务的是第一次跑全马、大概率还没买表的人。这不是降维竞争，是换一条准入。
Q：你的核心壁垒是什么？
技术上没有。规则引擎、课次上限、不补账、体感温度口径，对手随时能做。唯一复制不了的是主动劝降 —— 因为它会伤害他们的续订和完赛率叙事。也不是他们想不到，是商业化之后就做不出来了。这个项目能做，恰恰因为它没商业包袱 —— 说穿了，差异化是「穷的优势」。
Q：数据是真的吗？
项目真实做过，但当时埋点不完整，所以复盘时用真实的实体结构和口径把指标体系重建了一遍。数字是测算值，不是线上实测值。所有百分比都由整数计数算出，周粒度加总严格等于版本对比 —— 任意一个数字我都能说清它是从哪一层、按什么口径来的。
Q：这个项目和你的另一个 AI 项目（校园政策问答）有什么区别？
一个是静态知识的可信性问题（答案唯一，核心是「能不能信」，靠拒答边界和引用溯源解决）；一个是动态计划的可执行性问题（答案随状态变，核心是「能不能坚持」，靠约束重排和护栏解决）。前者考知识治理，后者考约束满足与风险治理，两者覆盖 AI 产品的两种核心命题，不重复。
