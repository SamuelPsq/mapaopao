Part I · 产品定义

01 项目概览

一段话讲清它是什么、不是什么

马跑跑不是一个「AI 生成训练计划」的工具，而是一个在天气、身体状态、时间冲突持续打断下，维护一份可执行计划的系统。生成计划只是一次性动作；真正的难点是第 3 周下雨、第 7 周膝盖发紧、第 11 周加班之后，这份计划还算不算数。围绕这条主线，产品实际长出了五个相互咬合的模块：

  • 今日卡：每天唯一需要看的一屏——今天练什么、什么配速、天气如何、打卡回执（累计/本周跑量是主视觉，下一节课是次要卡片）；
  • 周审视：每周一次的「教练谈话」——本周点评、AI 微调后的课表、跑步知识卡片；
  • 重排方案：计划被打断时的「为什么 + 怎么改」，候选先过护栏再打分出 1 主 1 备；
  • 指标页：周计划执行率、护栏有效性、AI 决策、AI 文案使用率——AI 是否真的在起作用，用数据回答；
  • 跑小助：挂在 RAG 知识库上的 AI 跑步助手，多轮对话记上下文，每个用户独立会话。

1.1 技术形态概览（一句话给工程师）

确定性规则引擎（VDOT 查表 + 周期模板，唯一数值来源）
        + 候选生成 × 护栏过滤 × 打分排序的重排引擎
        + 一层只负责「把结论说清楚」的 LLM 解释层（文本：DeepSeek）
        + 一个跑在 RAG 知识库上的多轮 AI 助手「跑小助」
        + 一个独立的视觉识别通道（Kimi 视觉模型，读成绩单/手表截图）
工程上最重要的一条约束，从第一天到现在没有变过 LLM 不参与任何数值计算。配速、跑量、增幅一律由规则引擎产出；模型只读入结构化结果做自然语言表达与定性微调，输出侧再做数值断言校验（见 13.4）。视觉识别是唯一的「模型出数字」通道，但每个数字都要过量纲、区间、配速合理性三道代码断言，校验不过直接拒用（见 13.6）。

1.2 技术选型（v2 同步版：真实在用的）

语言 / 框架Python + FastAPI规则引擎零框架依赖，pytest 直接跑；OpenAPI 文档零成本。与 v1 一致。

部署单机 uvicorn + vitestart.bat 一键拉起前后端；开发演示面板带「一键重启后端」（见 18）。

02 背景与问题定义

为什么已有的方案都没用 —— 这一章的论证在真实用户中继续成立

2.1 新人面对马拉松训练时的三种困境

困境具体表现现有方案为什么解决不了
看不懂书里有 VDOT 表、配速区间、周期化理论，但没人告诉他「我这周该跑几次、每次多快」书籍是知识体系，不是执行指令。从知识到行动之间缺一层参数化翻译
坚持不下来计划第一周能跟，第三周下雨断一次，第四周加班断一次，之后课表彻底脱离现实，直接放弃静态 PDF / 表格计划不具备容错能力。断一次就是不可逆的失败
不敢判断膝盖有点紧，今天的长距离到底跑不跑？跑怕伤，不跑怕掉队新人没有经验做这个判断，而书里只写了「感觉不适就减量」这种无法执行的话
问题定义（未变） 我们要解决的不是「生成一份科学的计划」，而是「让一个零基础的人，在 16 周里持续执行下去，并且不受伤」。 前者是知识检索问题，后者是约束满足 + 风险治理 + 行为驱动的复合问题。市面上绝大多数「AI 训练计划」工具停留在前者，所以计划很漂亮，但没人跑得完。

2.2 场景适配度自检

判断维度结论依据
有没有 ground truth有，且强训练原则来自公开书籍，VDOT 配速表、周增幅上限有唯一正确答案 → 可建测试、可算准确率、可转单测
错了有没有代价有，且延迟配速错 20 秒，一次间歇跑就能练废；受伤是数周累积 → 必须有独立护栏层
用户会不会反复用会16 周每周都看；真实场景中选修课按教学周使用、社团按训练周期使用，天然高频
AI 是必需还是点缀必需（部分）数值全部走规则；但「把调整原因说清楚」「跑步知识答疑」只有模型能做——AI 用在解释和知识，不用在计算
学生能否真做出来能书籍公开、天气 API 免费、规则引擎无需训练、文本 LLM 月成本以元计

3.1 落地场景：校园双通道

通道使用方式带来的产品约束
马拉松选修课作为教学工具：学生按教学周使用产品生成并执行个人计划，教师用周审视页看班级整体进度计划必须「可解释」——老师会问「为什么给他排这个」；护栏必须保守——学生受伤是教学事故

04 北极星与指标体系

指标能不能算出来，取决于埋点和口径 —— 而不是取决于写没写

4.1 北极星：周计划执行率（口径不变，实现见 07 / 15）

执行率(week) = 本周完成课次（含部分完成） ÷ 本周周初快照的计划课次
最容易踩空的一处：分母必须取周初快照 分母取「当前课表」的话，用户一触发重排、分母跟着变小，执行率被自动美化。工程上 plan_week_snapshot 表冻结每周课表，重排只写当前态、永不改快照。

4.2 指标页实际展示的四项（真实埋点口径）

指标口径回答的问题
周计划执行率完成课次 ÷ 周初快照课次；partial 计 1 次不按比例折算北极星：计划是否可执行
护栏有效性护栏触发并改变了方案的次数与占比（guard_audit 留痕）安全机制是真的在转，还是摆设
AI 决策AI 微调被采纳并落到课表的次数（AICase 表）AI 参与训练安排的深度
AI 文案使用率LLM 生成文案次数 ÷（LLM 生成 + 规则模板兜底）总次数；未配密钥自动走兜底不计失败解释层在真实服务还是形同虚设——这是「AI 产品还是套壳」的直接证据
口径声明（与 v1 的关系） v1 文档中的 v1–v3.1 四轮迭代数值（41.2% → 72.5% 等）是设计期的复盘推演口径，v1 文档已自我声明「复盘重建口径（自洽）」；本版不再把那组数字当作线上实测值引用，真实的产品演进记录见第 19 章。指标页四项指标则是真实埋点、真实计算的。

05 竞品分析与产品定位

它们其实不是一个物种；对手的哪些决定直接写成了我们的架构
v1 → v2 的变化 本章分析方法与结论在真实迭代中继续成立（尤其「缺练不补账」与「不做手表对接」两条），仅做压缩与口径更新；5.10 信息来源声明不变：竞品事实全部来自公开资料，未购买付费订阅做深度实测，被问到时直接说明。

5.1 两刀切法（不变）

第一刀 · 计划被打破时，重修成本由谁承担
静态产品：成本在用户身上；半自适应：成本在系统，但用户必须在它的数据前提之内；我们要的：成本在系统，且准入条件不排除任何人。
第二刀 · 自适应引擎烧的是什么燃料
烧手表生理数据 → 只服务有表且在生态里的人；烧主观上报 + 环境 + 可用天数 → 不排除任何人，但精度低一档。切完后，马跑跑的位置是「被他们的数据前提排除掉的那批人」。

5.2 竞品全景（L0–L5 分层，压缩版）

层代表它真正强的地方它排除谁
L0丹尼尔斯《跑步方程式》、汉森、Hal Higdon方法论的权威性与可追溯性，是所有 App 的知识上游假设「你时间充裕、天气配合、身体听话」
L1悦跑圈、咕咚、Nike Run Club记录 + 社区 + 赛事报名，解决「要不要跑」的动机问题想要结构化进阶计划的人
L2TrainingPeaks、Final Surge把「我是不是在过度训练」变得可量化（CTL/ATL/TSB）看不懂 PMC 图表的普通人
L3Garmin Coach日粒度紧贴生理状态，流程零摩擦没有 Garmin 手表的人（最硬的一道墙）
L4Runna、TrainAsONE把「缺练之后怎么修」做成核心叙事没有可穿戴设备的人
L5Keep（运动大模型 + Agent）多模态 + 长期记忆，一句话调度大量运动 Skill需要 16 周长周期守恒的人

真正构成参照的只有 L2–L5。把 NRC 和 Garmin Coach 并列成「同为跑步 App」，是把用户旅程的不同阶段当成了同类产品。

5.4 定位陈述（v2 同步版）

完整版：面向没有运动手表、第一次挑战全程马拉松的中文用户（当前落地为校内马拉松选修课与社团场景），基于公开跑步训练书籍中可计算的确定性结构生成 16 周计划；当计划被天气、身体状态或日程打断时，按「保关键课、放弃补账、牺牲辅助课」的原则在本周内重排，并给出可理解的解释；当进度不支持原目标时，主动建议降低目标；配套 RAG 知识助手回答训练与伤病问题，识别成绩单照片自动折算能力值。

15 秒版：「马跑跑是给没有跑表的新手做全马训练计划的产品。做得好的自适应 App 都依赖手表数据，我们把燃料换成主观上报加天气，代价是精度低一档，好处是任何人都能用——拍张成绩单照片它也能认识。」

5.5 诚实回答：我们不如它们的地方

  • 没有生理数据闭环：Garmin 的 VO₂Max / HRV / 睡眠 / 训练准备度每天重排，我们只能做到周级 + 用户主动上报。这不是「还没做」，是燃料决定了精度上限。
  • 没有数据飞轮：规则来自公开书籍，任何人都能写；数据量随时间增值的曲线我们没有。
  • 没有分发：756 个用户靠两个校园场景拉来，证明不了任何分发效率。
  • 验证周期短：单周期 16 周，缺跨季节、跨周期的长期验证，结论不能外推。

def pace_zones(vdot: float) -> dict:        # VDOT → 5 档配速区间（轻松/全马/阈值/间歇/重复）
    v = clamp(round(vdot), 30, 85)           # 越界 clamp，不抛异常

def vdot_from_recent_race(recent_km, recent_sec, ability):
    t_std = predict_time(recent_sec, recent_km, 10.0)   # Riegel 公式 k=1.06 折算 10km
    v = lookup_vdot_by_race("10k", t_std)
    if ability == "A_zero_base": v *= 0.92              # 零基础保守系数（见 3.2）
    return clamp(v, 30, 60)

MAX_WEEKLY_GAIN = 0.10                       # 全书最硬的一条安全规则：周增幅 ≤10%

机制真实实现
语义召回不是随机抽一条：用户连续两次打卡不足 → 优先「恢复/临时抱佛脚」类；上报膝盖酸痛 → 优先伤病条目；按用户状态与 tags 匹配，同组内轮换避免重复

8.3 跑小助：多轮 AI 助手（v2 新增）

  • 多轮上下文：先问「我膝盖疼」再问「那今天还能跑吗」能衔接上——服务端保存该用户会话历史并随消息下发；
  • 会话隔离：assistant_msg 按 user_id 隔离，退出登录即清空，杜绝账号间串话（这是真实修过的安全问题）；
  • RAG 带出处的回答：召回条目进 prompt，回答标注来自哪份知识文档；无密钥时降级为纯规则模板问答。

8.4 知识层分工的判断标准（不变）

面试金句判断哪些知识不该交给模型，比调 prompt 更重要。数值型知识（VDOT 45 → 5:07/km）在语义空间里几乎不可分辨，检索回来的往往是相邻段落，模型一插值数字就错；原则型知识（80/20 强度分布）交给 RAG 才合适。按知识类型分配处理方式，而不是全塞给向量库。

10 适应层实现：重排决策引擎 + 能力重估

整个产品的核心。成败不取决于「能不能生成」，取决于「被打断之后怎么修」

10.1 触发源与上下文（真实）

触发源提前获知处理倾向
天气硬约束（暴雨/雷电/高温体感）提前 1–3 天替换（室内/交叉）或顺延
身体状态上报（酸痛/睡眠/疲劳，打卡流程内嵌采集）当天降级，严重时压缩
打卡偏差（实际 vs 计划差 ≥30%）当天追问「临时起意 / 强度不匹配」，后者触发能力重估
实际成绩显著超出 VDOT（超额完成）当天弹窗建议进阶 → 重算 VDOT 刷新未来周

10.2 策略库与打分（真实实现：adapt 包）

不是 if-else 链，是「候选生成 → 全量过护栏 → 打分排序」。6 个候选生成器：gen_replace / gen_downgrade / gen_compress / gen_postpone / gen_deload / gen_noop（永远保留「什么都不做 / 标记降载」作为兜底）。打分函数与 v1 设计一致：

score = 0.55 × p_complete(本周交付概率，逐日累乘存活概率)
      + 0.30 × key_stimulus_kept(关键训练刺激保留率，按强度当量算不是按公里算)
      + 0.15 × safety_margin(安全余量)
这条打分函数天然推出的反直觉排序顺延看起来「什么都没少」（削减 0 km），但交付概率最低——课推到更晚，剩余每天都还有被打断概率，累乘下来整体交付率反而下降；压缩砍的是低强度辅助课，关键刺激保留率只掉一点，却把课压进确定能跑的日子。重排的目标不是「把课排完」，而是「保住本周的训练刺激」。

10.3 compensate_across_week = False：一条不会回头的决定

本周缺口标记为沉没成本（week.is_dropped），下周按原周期继续，没有任何 append / rebalance。沉淀的规则：训练计划的缺口是沉没成本，不可补偿；补偿会把它从「一次性损失」变成「复利负担」。正确的容错方式是「重新分配未来」，不是「偿还过去」。

10.4 AI 微调（tune 包）：让 LLM 参与排课，但只作为微调

微调课表 = LLM(本周课表 + 用户状态 + 结构红线清单) → 候选新课表
for 红线 in [轻松跑距离 ≤ 长距离距离, 周增幅 ≤ 10%, 长距离次日必须休息, ...]:
    if 违反(红线, 候选): 拒用，回退规则模板

真实教训：AI 微调曾把轻松跑拉得比长距离还长——是靠结构红线断言拦下来的，不是 prompt 够聪明。这条红线清单已沉淀进 RAG 知识库，prompt 显式引用。LLM 的建议权必须配代码的否决权。

10.5 能力重估：让执行结果反过来作用于未来

reevaluate_vdot(logs):  new = implied_vdot(最佳一次实测)
    if abs(new - user.vdot) >= 1.5:        # 死区，避免抖动
        user.vdot = new
        refresh_future_weeks(user)          # 只刷新「尚未开始」的周，已执行的周永远不动

真实入口有三个：① 打卡偏差 ≥30% 且用户确认「强度不匹配」；② 超额完成进阶确认；③ 智能识别成绩确认。入口不同，归一化到同一条重估逻辑——应用规则只有一套，避免分散的特例。

11 护栏层实现

三条红线 + 两条体感红线 + 一套结构断言，一个不可绕过的纯函数，一次都不允许例外

11.1 规则清单（真实实现：guard 包 + 应用层校验）

规则判定依据
R_WEEKLY_GAIN周跑量增幅 > 10% → 截断 / 拦截书籍里最硬的一条；受伤最主要的近因是负荷突增
R_CONSEC_HARD任意连续 3 天高强度 → 拦截重排受伤最主要的近因是高强度堆叠，不是单次强度过高
R_INJURY_WINDOW14 天内伤痛上报 ≥2 次 → 强制降载一周（只保留轻松跑，不允许补偿）滞后信号的前置化；命中后给今日卡降载提示并在周审视标注
睡眠/疲劳红线（v2 新增）连续两天睡眠 <5h 或疲劳 >7 分 → 今日卡提示「今天强度课建议降一档」主观上报的数据第一优先级用途：当日安全
结构红线（tune 层）轻松跑 ≤ 长距离、周增幅 ≤10%、长距离次日必须休息AI 微调的输出约束，见 10.4

11.2 为什么护栏必须独立 + 必须留痕

重排的目标函数是「这周怎么排最合理」，护栏的目标函数是「这个方案会不会伤人」，两者会冲突——用户连着几天没跑，重排想让他补回来，护栏必须拦住。混在一起写，优化目标会悄悄把安全吃掉（执行率短期可见，受伤几周后才显现）。工程上 guard 是独立纯函数，所有候选（包括 NOOP）都必须过它，且每次调用写 guard_audit：block 记，pass 也记——只有知道「差点被拦下但通过了」的占比，才能判断红线阈值是不是定得太松。

11.3 BMI 保守模式（v2 新增）

BMI 偏大的用户自动进入保守规划：起步强度降档、课表更温和，且周审视页显式标注「保守规划周（BMI 适配）」。设计上把「为什么计划和别人不一样」讲清楚——体重大的用户明确知道计划温和是刻意的。身高注册后锁定不可改（BMI 口径稳定），体重可在指标页实时修改并即时联动规划。

11.4 反增长设计：敢让用户少练

连续 3 周关键课完成率 <50% → 主动建议降目标（全马降半马 / 延期 / 坚持但本周自动降载）。命中后系统不允许自动改目标，必须用户点确认——建议权在产品，决定权在用户。训练类产品最怕的不是用户少，是用户在赛道上出事；产品敢说「你的目标定高了」，是真正站在用户立场上的判断。

13.4 输出侧数值断言（防幻觉的最后一道闸）

def assert_no_hallucination(text, facts) -> bool:
    allowed = {fmt(n) for n in flatten_numbers(facts)}
    return {fmt(n) for n in re.findall(r"\d+(?:\.\d+)?", text)} <= allowed
这条断言比任何 prompt 都管用它把「模型不许编数字」从一句 prompt 里的话，变成一条会红的测试。模型一旦编数字，断言立刻拦截走模板。

只报涨的数字等于没做过项目——这一章全是真实发生过的坑
1打卡按钮从四个浓缩成一个
现象
「完成了 / 只跑了一部分 / 超额完成」三选一，用户在「跑完了但比计划多一点」时犹豫几秒就放弃打卡
修复
浓缩为「今日打卡」一个按钮，距离时间默认值=计划值、可齿轮调整；偏差 ≥30% 才追问原因并分流处理
沉淀
每个用户决策点都要能回答「不做这个选择用户会失去什么」，答不上来就砍——选项多 ≠ 体验好
2AI 微调把轻松跑拉得比长距离还长
现象
周审视页 AI 微调输出明显违背训练学常识的课表
修复
不指望 prompt 变聪明，加结构红线断言（轻松跑 ≤ 长距离、周增幅 ≤10%、长距离次日必须休息），违反即拒用回退模板；红线清单沉淀进 RAG 知识库供 prompt 引用
沉淀
LLM 的建议权必须配代码的否决权——「用代码校验代替 prompt 约束」
3训练天数改成 6/7 天「什么都没变」
现象
用户在指标页把每周天数从 5 改成 6/7，课表逐节不变，像是 bug
根因
课次上限 6→5、7→5（训练学：新手每周超 5 课风险大于收益），不是 bug 是特性——但没有告诉用户
修复
周审视本周点评显式提示「课次已达安全上限」；关联修复：改任何参数只重排未开始的周，不再重建计划清空进度
4「一键重启后端」装错了地方 + 跑小助串话
现象 ①
后端被挂起后重启按钮毫无反应——重启开关调的是后端自己的接口，后端死了开关跟着死
修复 ①
重启开关挪到前端 dev server（vite 中间件 + 看护脚本 kill 模式），后端全挂也能拉起
现象 ②
跑小助会话共享：A 用户能看到 B 用户的聊天记录
修复 ②
会话按 user_id 隔离 + 退出登录即清空；回归测试补进 test_api_assistant
沉淀
账号隔离是 AI 功能的默认要求，不是增强项——做多助手的第一课

21 面试速查卡（v3.2 同步版）

完整问答见《金科产品助理-面试QA.md》
Q：这不就是把书塞进数据库然后调大模型吗？
知识层是拆开的：数值知识走确定性规则引擎（VDOT 查表唯一数值来源），LLM 只做解释、定性微调和知识问答。防幻觉靠的不是 prompt——所有 LLM 输出过代码数值断言（文案出现的数字必须在 facts 里；微调课表过结构红线；识别成绩过量纲/区间/配速三道断言），校验不过直接拦截回退模板。判断哪些知识不该交给模型，比调 prompt 更重要。
Q：RAG / 召回 / prompt 调优在你的项目里真实落地了吗，在哪？
三处。① 知识库：docs/ 下三份结构化知识文档（训练原则/跑者经验/伤病康复），三分块格式 + tags，启动时解析；② 召回：周审视「跑步知识」卡片不是随机抽——连续打卡不足优先恢复类、报过酸痛优先伤病类，按用户状态匹配 tags；跑小助问答也走同一召回池喂上下文；③ prompt 版本化：全部 prompt 集中在 server/prompts.py 随 Git 管理，每次改动可回滚。AI 文案使用率指标专门监控 LLM 与规则兜底的占比。
Q：重排引擎是怎么决策的？和一堆 if-else 有什么区别？
「候选生成 → 全量过护栏 → 打分排序」。6 个候选生成器（替换/降级/压缩/顺延/降载/不做事），全部过独立护栏函数并留痕，打分 = 0.55×本周交付概率（逐日累乘）+ 0.30×关键刺激保留率 + 0.15×安全余量。这套打分自然把「压缩」排第一、「顺延」压到最后：顺延削减 0km 但只是把问题推到明天，交付概率最低。
Q：AI 参与训练安排，不怕它乱排课吗？
AI 只有建议权。微调输出必须过结构红线断言（轻松跑 ≤ 长距离、周增幅 ≤10%、长距离次日必须休息），违反即拒用回退规则模板。真实事故：AI 曾把轻松跑拉得比长距离还长，是红线拦下来的——用代码校验代替 prompt 约束。
Q：你的核心壁垒是什么？
技术上没有。规则引擎、体感温度、不补账，对手随时能做。唯一复制不了的是主动劝降——它损害续订逻辑和完赛率叙事。也不是对手想不到，是商业化之后做不出来。这个项目能做，恰恰因为它没有商业包袱。
Q：数据是真的吗？
功能、事故、指标口径全部真实，756 名用户来自选修课与社团两个真实场景。需要坦白：v1 文档里的四轮迭代百分比是设计期复盘重建口径（当时埋点不完整），本文档 v2 已把那一章替换为四个有 Git 记录的真实事故；指标页四项指标是真实埋点真实计算。
Q：B 端需求是怎么挖掘出来的？为什么不做成「老师监控学生跑没跑步」？
实验室的原话是「硬通货是纵向数据」。普通体测一年一个断面，而马跑跑在生产周粒度的连续追踪：16 周训练执行 + 主观状态上报（睡眠/疲劳/酸痛）+ 伤痛事件 + 天气响应，全部带时间戳、口径统一（执行率有快照冻结防污染）。这条需求链路是：C 端产品先跑起来产生数据资产 → 拿着资产找合作方 → 合作方的真实诉求（发论文要脱敏导出、过伦理要知情同意、做干预研究要线上问卷）反向定义 B 端功能。「监控学生」这个方向一开始就排除了——它是管理视角，会诱导老师盯人而不是看数据，且与 C 端「安全优先、主动劝降」的产品价值观直接冲突。B 端是科研视角：看分布、看趋势、看变量关系，不看个人。
Q：给实验室的导出数据怎么脱敏？怎么证明脱干净了？
三层。①不可逆假名：用户名/学号替换为加盐 SHA-1（12 位），盐值每次导出随机生成且不入包——拿到 ZIP 的人没有任何材料反推身份；②可审计：盐的摘要、导出人、队列、日期区间写 export_log，谁导了什么随时可查；③可预览：导出前先调 preview 看字段清单和行数预估，数据本身不经过预览接口。还有两个科研细节：同一学生跨表、跨次导出的假名一致（盐按批次稳定映射），纵向分析能对上人；周问卷未填也保留一行作分母，防止「删掉未填样本」拔高回收率。脱敏不是技术问题，是信任问题——所以每一层都留了对实验室可验证的证据。
Q：B 端数据怎么反哺 C 端？全自动调参为什么不做？
v3.2 落了第一条闭环：周一扫描 active 计划，连续 3 周关键课完成率均 <50%（任意一周达标即排除，区分「偶然没跑好」和「结构性跑不动」）自动生成周量系数 ×0.9 的建议，教师采纳后只缩放「今天之后」的课、周跑量过护栏压回、进度一笔不动。全自动不做，两个原因：①改的是学生的训练负荷，机器直接改人身上的计划必须过人审——这是伦理问题，不只是工程问题；②统计信号会误伤个体，三周低完成率也可能是考试周，让了解学生的老师做最后一公里的判断。和 LLM 微调过结构红线是同一套哲学：系统的建议权，必须配人的否决权。
Q：B 端功能会不会拖垮 C 端体验？
不会，因为 B 端的第一条设计原则是「零额外负担」：除了问卷（本来就要线上化），B 端没有一条数据是让用户额外手填的——打卡、状态上报、伤痛记录在 C 端流程里顺手采集，科研数据是副产品。工程上 C/B 共用一张 account 表靠 role 分流（不做两套登录），问卷实例生成放在周日 20:07 的低峰 cron，导出是教师要数据时才跑的离线动作。C 端用户感知到的唯一变化是注册时多一个必勾的协议框——这恰恰是伦理要求，不是负担。

22 实验室 B 端模块（v3.2）

产品对外是 C 端训练工具，对合作实验室是一台「纵向数据生产机」——这一章讲 B 端为什么存在、每一块怎么实现

22.1 B 端为什么存在：实验室的硬通货是纵向数据

校体育学院运动与健康实验中心的需求不是「看学生跑没跑步」，而是科研级纵向追踪数据。马跑跑恰好生产这种稀缺品：16 周连续的训练执行数据 + 主观状态上报（睡眠/疲劳/酸痛）+ 伤痛事件 + 天气响应记录，全部带时间戳、口径统一（执行率有 plan_week_snapshot 快照冻结防污染）。普通体测一年一个断面，这里是周粒度纵向追踪。交换条件是实验室提供伦理审查通道与学术背书——所以 B 端第一批功能按「过伦理审查 + 能直接进统计软件」的标准做。

B 端的第一条设计原则 B 端没有一条数据是让用户额外手填的（问卷除外）——全部建立在 C 端既有数据资产上。用户只是在按计划训练，科研数据是「顺手生产」的副产品。不产生额外负担，纵向数据才可持续。

22.2 知情同意层（伦理审查的入场券）

设计实现
强制同意注册页必须勾选《数据使用协议》才能提交（不勾选无法注册），前端写死在注册表单校验里
协议版本化协议文本与版本号由 GET /v1/consent/doc 下发（未登录可读——注册页必须能读到协议才能同意）；当前版本 CONSENT_VERSION = "1.0"
同意留痕同意记录单独成表 consent_record（user_id + version + 时间），注册时写入；协议升级后可按版本圈出需重新同意的用户

22.3 匿名化数据导出（实验室拿去发论文的门票）

教师一键导出 ZIP 包 = 4 张 CSV + dictionary.md（变量字典）+ readme.md（协议版本与脱敏说明）。导出前先走 /v1/lab/export/preview 看字段清单与行数预估，不返回数据本身。

文件口径
weekly_training.csv一行 = 一名学生 × 一周：周计划量 / 实际量 / 关键课完成率 / 是否降载（来源 plan_week_snapshot 冻结口径，非运行时重算）
daily_state.csv一行 = 一名学生 × 一天：打卡状态 / 酸痛部位 / 关节不适 / 睡眠 / 疲劳 / 跑中体感
survey_weekly.csv一行 = 一名学生 × 一周：周问卷答案展开为列；未填也保留一行（回收率的分母，丢掉未填样本是科研常见作弊）
events.csv事件流：打卡 / 重排 / 劝降 / 进阶 / 天气响应等关键事件，带时间戳
脱敏怎么做才算「不可逆」 用户名/学号 → 加盐 SHA-1 假名（12 位，如 a3f9c1d2e4b7）。盐值每次导出随机生成且不入包——包里只有假名，反推不出是谁；盐的 SHA 摘要写进 export_log（谁 / 什么时间 / 什么队列 / 什么日期区间 / 盐摘要），保证每次导出可审计、可复现口径。同一学生跨表、跨次导出的假名一致（盐按导出批次稳定映射），纵向分析能对上人。

22.4 问卷系统（把纸质问卷线上化，顺手把回收率做成周粒度指标）

设计实现
三种问卷pre（前测）/ weekly（周问卷）/ post（后测）；题型 likert7（7 点量表）/ bool / text，逐题必填校验

22.5 调参闭环（M3）：B 端数据反哺 C 端算法

B 端存在的第二层意义：大量真实训练数据可以反过来校准 C 端的课表安排。v3.2 落地第一条闭环——「学生跑不动」的信号从 B 端回到 C 端计划：

1周一 00:32 生成建议（纯规则，非 LLM）
触发
active 计划连续 3 周关键课完成率均 <50%（任意一周 ≥50% 即排除——一周没跑好是偶然，三周是结构性信号）
跳过
近 14 天伤痛上报 ≥2 的计划不提议（避免与护栏降载叠加）
去重
同计划已有 pending 建议不再生成；建议文案写给人看（「平均完成率 41%，建议周量系数下调 10%，并建议与学生沟通训练时间安排」）
2教师采纳 → 只动未来，不清过去
落表
采纳写 plan_config（scope=plan，volume_multiplier=0.9，proposed_by=system，approved）——配置是谁、何时、因何改的，全部留痕
应用
系数乘到今天之后的未执行课程（钳制 0.5~1.0，只收紧不放松）；今天已过的课、已有记录一笔不动——与 C 端「改参数不清进度」同一铁律
兜底
重算后的周跑量再过一遍护栏红线（周增幅 ≤10%）压回——收紧方向也受代码约束，与第 13 章「LLM 的建议权必须配代码的否决权」同源

完整引擎（gain_cap / aux_cap_ratio 字段已在 plan_config 落表，按分组变量调参）留 v3.3；v3.2 先把「采集 → 建议 → 人审 → 应用 → 留痕」的闭环骨架跑通。全自动调参不做：改的是学生的训练负荷，必须过人审——这是伦理问题，不只是工程问题。
